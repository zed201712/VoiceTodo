# 存檔：提醒事項

## Problem Statement

待辦原本存在 App 自己的 JSON 檔，和使用者真正在用的 Apple 提醒事項是兩份資料：要先匯入，App 裡改了也不會回到提醒事項，demo 時使用者說的話改不到自己真正的待辦。

## Solution

Apple 提醒事項（EventKit）就是待辦的存檔：App 讀取所有的提醒事項成為待辦，每個任務結束後把待辦的改變寫回提醒事項。原本的 JSON 存檔捨棄，不轉移。

App 內部仍然以整份待辦（`[Todo]`）運作：任務的快照與還原、undo／redo 都是整份換掉（見 [recovery](recovery.md)）。存檔的介面也是整份讀、整份寫，怎麼變成提醒事項的新增、修改、刪除，是存檔實作的內部細節；之後改回 JSON 只換實作，不改介面。

一句話：**提醒事項就是存檔；App 整份讀寫，差異、刪除快照、alarm 都在存檔內部處理。**

## User Stories

1. 作為使用者，我想打開 App 就看到提醒事項裡所有還沒完成的項目，包括沒有日期的；打開「顯示已完成」才看已完成的，多年累積的已完成項目不拖慢開啟。
2. 作為使用者，我想用說的新增、修改、完成、刪除，提醒事項 App 裡跟著變。
3. 作為使用者，我想刪除後 undo，那筆提醒事項回到原本的清單，備註等資料都還在。
4. 作為使用者，我想在提醒事項 App 或其他裝置改了東西，回到這個 App 就看得到。
5. 作為使用者，我想沒給提醒事項權限時，小精靈告訴我要去哪裡打開。
6. 作為開發者，我想用一份固定的測試待辦重現測試，又不會改到自己真實的提醒事項。

## Implementation Decisions

### 介面

存檔有四件事，和背後是提醒事項還是 JSON 無關：

- **讀取**（非同步）：回傳常用的那部分待辦；需要權限時在這裡請求。沒有權限或讀取失敗時丟出錯誤，附上原因。
- **讀取其餘的**（非同步）：回傳讀取時沒給的其餘待辦（見「延遲讀取」）；JSON 這種一次就能全讀的存檔回傳空的。
- **寫入**：給整份待辦，存檔自己算出差異並套用；沒讀過的項目不受影響。
- **外部變動**：存檔被 App 以外的地方改了時通知 App；JSON 這種只有 App 會改的存檔永遠不通知。

`Todo` 不帶提醒事項的任何資料（識別碼、清單、備註…）：這些都只在存檔的實作裡。

### 讀取

- 範圍：所有清單裡所有未完成的提醒事項（`predicateForIncompleteReminders`，開始與結束日期都不給，沒有到期日的也包括在內）。已完成的見「延遲讀取」。
- 每次讀取在測試紀錄與 console 記一行：讀到幾筆、花了幾毫秒（實機上確認效率）。
- 每筆提醒事項變成一筆待辦：
  - 內容：標題去掉前後空白。標題空白的不讀進來，App 也不會改到它。
  - 日期：到期日的那一天；沒有到期日就是**沒有日期的待辦**（見 [todos](todos.md) 的「沒有日期的待辦」）。
  - 時間：到期日有時間就用它；只有日期時沒有時間。
  - 完成：提醒事項的完成狀態。
- 重複的提醒事項：EventKit 給的這一次的到期日，當成單次的待辦（App 沒有重複的待辦）。
- 待辦的 id 是 App 內部的編號：存檔記住每個 id 對應哪一筆提醒事項；重新讀取時，同一筆提醒事項沿用原本的 id，所以重新讀取不會打亂 undo 的歷史與黑板。

### 延遲讀取

已完成的提醒事項會一直累積（用了幾年可能上千筆），但只有黑板的「完成」勾選時才看得到，所以開啟時不讀，需要時才讀：

- 存檔記一個旗標：已完成的讀過了沒。開啟時是沒有。
- 「完成」從沒勾變成勾選、旗標是沒有時，先讀取所有已完成的提醒事項，讀完設旗標，之後不再讀（怎麼觸發見 [todos](todos.md) 的「黑板」）。App 啟動時「完成」本來就勾選的，開啟時一起讀。
- 讀進來的待辦加進目前的待辦，**也補進 undo／redo 歷史的每一個狀態**：它們本來就一直存在，只是之前沒讀。沒補的話，undo 換回舊的狀態時，存檔會以為它們被刪了，真的從提醒事項刪掉。
- 讀取在任務之間進行（點的開關、或執行設定顯示、刪除完成之前），不在任務的快照之後。
- 還沒讀的已完成提醒事項不在待辦裡，寫入時也不會被當成刪除：寫入只比較存檔讀過的項目。
- 讀取失敗：不勾選「完成」，回報失敗的原因；旗標維持沒有，下次勾選再讀。

### 寫入

和上次讀取或寫入的那份比較，依 id 找出差異，一次寫入（全部成功或全部不寫）：

- **新增**（新的 id）：在提醒事項的預設清單建立一筆。有時間的加上 alarm（見 [notifications](notifications.md)）。
- **修改**（同一個 id，內容不同）：只改標題、到期日、完成三項；備註、清單、優先順序、子任務等 App 看不到的資料不動。改到日期或時間時，alarm 與開始日期照 [notifications](notifications.md) 的規則跟著移。
- **刪除**（id 不見了）：從提醒事項刪除，刪除前先留下刪除快照（見下一節）。
- 寫入失敗只印到 console：資料仍在記憶體裡，App 可以繼續用（和原本的 JSON 存檔相同）。
- 什麼時候寫入照舊：每個任務結束後、undo／redo 後；任務進行中不寫入（見 [todos](todos.md) 的「資料」）。

### 刪除快照

刪除就是真的從提醒事項刪掉。但 undo 會把刪掉的待辦加回來，只靠待辦本身（內容、日期、時間、完成）重建，會遺失備註、清單等資料，所以：

- 刪除一筆提醒事項之前，存檔把 EventKit 讀得到的所有資料記成這個 id 的**刪除快照**（類似業界的 snapshot（快照）；不是 tombstone（墓碑），tombstone 只留「已刪除」的標記，不保留資料）：清單、備註、URL、優先順序、alarm、重複規則、開始日期、地點。
- 之後寫入時，同一個 id 又出現（undo 刪除、取消後還原），用刪除快照重建一筆新的提醒事項：放回原本的清單，帶回刪除快照裡的資料，再套用待辦的內容、日期、時間與完成。原本的清單已經不在時，放進預設清單。
- 刪除快照只在這次開啟期間有效，和 undo 的歷史一樣不跨 App 重開。
- 重建的提醒事項是新的一筆，提醒事項的識別碼和原本不同；存檔把這個 id 改成對應新的那筆。
- EventKit 沒有開放的資料（子任務、標籤、圖片、旗標）刪除後救不回來，undo 也一樣。

### 外部變動

使用者可能同時在提醒事項 App 或其他裝置改資料。

- 存檔收到提醒事項的變動（`EKEventStoreChanged`），或 App 回到前景時，重新讀取。範圍和目前讀過的相同：所有未完成的、存檔已經知道的每一筆（依識別碼，例如這次開啟後在 App 裡設成完成的），旗標是有時再加上所有已完成的。已經知道、但讀不到的，就是在別處被刪了。
- 讀回來的和 App 記憶體裡的待辦相同：是 App 自己寫入造成的，忽略。
- 不同：整份換成讀回來的待辦，清空 undo／redo 的歷史（undo 回去會蓋掉別處的修改），對話流加一則「提醒事項有變動，已更新」（見 [ui](ui.md) 的「對話流」）。黑板的範圍不動。
- 不同時，測試紀錄逐筆記下差異（`[存檔] 外部變動的差異`），每筆帶待辦的 id、完成、日期、時間與加引號的內容，修改的列出前後；用來在實機上確認是不是誤判（例如識別碼換了、內容的前後空白），可以用「分享測試紀錄」帶回來。
- 目前的結果正在執行任務、等釐清或刪除確認時先不套用，任務結束後再套用。
- 反過來，任務之外的背景讀取（外部變動、點開關時的延遲讀取、重新開始、測試清單）進行中，不開始下一個任務、不能點：讀回來的待辦會整份換掉，任務做到一半的改變會被蓋掉。App 自己寫入也會觸發外部變動，連續說幾句話時很容易遇到。

### 權限

- App 啟動時讀取，第一次會跳出系統的提醒事項權限對話框。系統只會跳一次，之後只能請使用者自己到系統設定打開。
- 沒有權限或讀取失敗時，App 沒有存檔：
  - 黑板是空的。
  - 待辦的所有指令都放棄（包括查詢、黑板、復原），回話回報「沒有取用提醒事項的權限，請到系統設定允許」或讀取失敗的原因；聊天與查天氣照常。
  - 開啟 App 時開場問候之後一則回話說同一句話；沒有可以使用的 AI 時，「無法運作」的提示接在後面（見 [settings](settings.md)）。
- App 回到前景時重新讀取：使用者在系統設定打開權限後，回到 App 就能用。
- 權限對話框的說明（`NSRemindersFullAccessUsageDescription`，在 build settings）要說出 App 會讀取所有提醒事項，並把新增、修改、完成、刪除寫回提醒事項；macOS App Sandbox 開啟行事曆（含提醒事項）存取。

### 測試清單

開發者測試時要一份固定的待辦，又不能改到真實的提醒事項（例如測「刪除全部」會刪掉黑板上全部的提醒事項）。所以除錯 UI 有「測試清單」開關（見 [ui](ui.md) 的「除錯 UI」，只在 macOS）：

- 打開：在提醒事項建立「VoiceTodo 測試」清單，放進測試待辦（見 [judge-cases](../eval/judge-cases.md) 的測試待辦），之後存檔只讀寫這個清單，新增的待辦也放在這裡；真實的提醒事項讀不到，也改不到。
- 打開時已經有同名的清單（上次沒關就結束 App）：先刪掉再建立。
- 重新開始：測試清單換回測試待辦（刪掉清單再建立）。
- 關閉：刪除這個清單，回到讀寫所有清單，重新讀取。
- 開關不存檔，App 啟動時一律關閉；上次沒關就結束 App 時，清單留在提醒事項裡，下次打開開關時處理。
- 換清單時清空 undo／redo 的歷史與刪除快照，延遲讀取的旗標回到沒有。

### 重新開始

除錯 UI 的「重新開始」不改待辦：清空測試紀錄、三個佇列、等待與 undo／redo 的歷史，再從存檔重新讀取（見 [ui](ui.md) 的「除錯 UI」）。測試清單開關打開時例外，見「測試清單」。

## Testing Decisions

- 差異（純邏輯，macOS 單元測試）：給上次與這次的待辦，算出新增、修改、刪除；沒變的不寫；被刪的 id 又出現時是「用刪除快照重建」。
- 到期日（純邏輯）：新的一筆（包括用刪除快照重建、日期沒變的）一定寫到期日；已經存在的只在日期或時間改變時寫。
- 提醒事項與待辦的轉換（純邏輯）：到期日只有日期、有時間、沒有到期日；標題空白不讀。
- 延遲讀取（假的存檔）：開啟時只有未完成的；第一次勾選「完成」才讀其餘的，第二次不讀；讀進來的補進 undo 歷史，undo 之後已完成的仍在、存檔沒有刪除；讀取失敗不勾選；「完成」已勾選時開啟就讀。
- 小精靈（假的存檔）：
  - 沒有權限、讀取失敗：黑板空的、待辦的指令全部放棄並回報原因、聊天與查天氣照常
  - 外部變動：和記憶體相同時忽略；不同時換掉、清空 undo，並在測試紀錄逐筆記下差異；任務進行中延到任務結束；背景讀取中不開始任務，讀完才執行，兩邊的改變都保留
  - 重新開始重新讀取，不改待辦
- EventKit 本身不跑單元測試（macOS 單元測試不碰提醒事項），手動驗證（實機）：
  - [ ] 第一次開啟跳出提醒事項的權限對話框，允許後看到所有未完成的提醒事項，包括沒有日期的；打開「顯示已完成」後看到已完成的
  - [ ] 測試紀錄的讀取筆數與毫秒，記下實際的數字
  - [ ] 打開測試清單：提醒事項 App 出現「VoiceTodo 測試」清單與測試待辦，黑板只有它們；說「刪除全部」只刪測試清單；關閉後清單消失，真實的提醒事項都還在
  - [ ] 新增、修改、設定完成、刪除後，提醒事項 App 裡跟著變；修改不會動到備註與清單
  - [ ] 刪除一筆有備註、在非預設清單的提醒事項後 undo：回到原本的清單，備註與到期日還在，undo 按鈕沒有變灰
  - [ ] 在提醒事項 App 改一筆，回到 App 黑板跟著變，undo 按鈕變灰
  - [ ] 拒絕權限：說任何指令都回報要去系統設定；打開權限後回到 App 就能用
  - [ ] 把重複的提醒事項設成完成，觀察提醒事項 App 與黑板的結果（EventKit 對重複項目的處理未確認）

## Out of Scope

- 轉移舊的 JSON 存檔
- 選擇要讀取的清單；新增時指定清單
- 子任務、標籤、圖片、旗標、地點等 EventKit 沒開放或 App 看不到的資料的編輯
- 重複的待辦
- 讀取失敗時退回 JSON 存檔
- 行事曆（EKEvent）的事件
