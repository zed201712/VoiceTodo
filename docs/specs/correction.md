# 校正階段

## Problem Statement

語音辨識會出現同音錯字，例如「10月6號麵是」「跟小每出去玩」。錯字會進到待辦的內容，或讓內容關鍵字找不到黑板上的待辦。語音辨識完美時，這個階段不需要存在。

之前的校正讓 AI 依執行器的定義重寫整句，常把正確的句子改錯（「看牙醫」→「去看牙醫」、「新增」→「新增待辦」），因此關閉過。

## Solution

自動 AI 結合畫面資訊（使用者開口時看到的黑板、最後一則回話與釐清的問題，見 [screen-info](screen-info.md)）與常識，只修正錯別字；App 只採用字數與數字不變的結果。校正是加分的步驟，不需要一定成功：不採用或失敗時，原句直接進判斷。

一句話：**用畫面上的資訊與常識修錯別字，字數與數字不變才採用，否則用原句。**

## User Stories

1. 作為使用者，我想辨識錯字依常識被修正（「10月6號麵是」→「10月6號面試」）。
2. 作為使用者，我想說到黑板上已有的人名、名詞時，錯字被修正成黑板上的寫法（黑板有「跟小美吃飯」，「跟小每出去玩」→「跟小美出去玩」）。
3. 作為使用者，我想正確的句子不被改動，校正失敗也不影響操作。
4. 作為開發者，我想在除錯 UI 與測試紀錄看到校正前後的文字與是否採用，知道錯字是在哪一階段被修正或改錯。

## Implementation Decisions

### 規則校正

一句話定稿時（任何關鍵字比對之前），先由規則校正處理語音辨識的寫法：

- 拿掉多餘的空白：空白兩邊都是英文字母或數字才保留，其他都拿掉（「10月 6號有什麼事 ？」→「10月6號有什麼事？」、「買 iPhone 17」→「買iPhone 17」）。語音辨識常在字之間加空白，AI 校正會把它拿掉，字數就不同而不採用。
- 時刻改成幾點幾分：`H:MM`（冒號也可以是全形）改成「H點」或「H點M分」（「晚上9:00」→「晚上9點」、「9:30」→「9點30分」）。語音辨識把時間寫成「9:00」，日期與時間解析只認得「9點」；AI 判斷照抄時會放棄（2026-10-08 實測 Foundation Models）。冒號後面不是兩位數的不改（「3:2」）。

- 每句話都做，包括關鍵字、手動 AI 與沒有 AI 校正時；之後的關鍵字比對、AI 校正（字數比較的基準）、判斷與聊天都用處理後的句子。重試時沿用。
- 有改動時，測試紀錄記一行「校正：規則：<原文> → <處理後>」；對話流裡的這句話換成處理後的句子。

### 什麼時候校正

- 只校正**要送去判斷的話**（一般判斷、釐清後判斷）。關鍵字照舊用原句判斷、不校正：關閉語音、重試／略過、復原／重做、顯示全部、上一頁／下一頁、刪除確認的關鍵字回答。刪除確認的回答不校正；回答是 other 時轉成釐清後判斷，那時才校正。
- 每句話只校正一次：判斷失敗後重試時，沿用同一份校正結果，不再呼叫校正。
- 手動 AI 時不校正，原句直接進判斷。目前的自動 AI 沒有校正功能（Foundation Models、Ollama）或沒有自動 AI 時也不校正。

### 和判斷同時進行

校正和「用原句的判斷」同時開始，不等校正完才判斷；一般判斷的這一段在背景的執行佇列裡進行（見 [queue](queue.md)）：校正多半不改句子，同時進行就省下校正的時間（2026-10-03 以 gemini-3.1-flash-lite 實測 10 句：校正平均 1.19 秒、判斷 2.02 秒，校正先回來 9 次）。

一句話：**校正採用了新句子，就作廢原句的判斷、用新句子重判；否則用原句的判斷。**

| 校正 | 原句的判斷 | 結果 |
|---|---|---|
| 未修改、字數不同、失敗、不校正 | 成功 | 用原句的判斷 |
| 未修改、字數不同、失敗、不校正 | 失敗 | 進入錯誤確認（重試的句子是原句） |
| 採用新句子 | 成功、失敗或還沒回來 | 作廢：還在跑就取消；用新句子重新判斷 |

- 兩邊都回來才決定：判斷先回來時等校正；原句的判斷不會在校正結束前執行任何指令，也不會進入聊天（見 [chat](chat.md)）。
- 作廢的判斷不算判斷失敗，不進入錯誤確認；只有採用新句子時，這句話才多一次判斷呼叫。

### 校正請求

每句話一次呼叫，不保留紀錄。請求文字是畫面資訊（見 [screen-info](screen-info.md)），「使用者說」是這句話的原文：

```
現在：2026/10/2（五）14:30
黑板：目前 10/2–10/8
☐ 10/3（六） 12:00 跟小美吃飯
☐ 10/5（一） 18:00 跟小明出去玩
小精靈說：要刪除哪一個？
小精靈剛才問：要刪除哪一個？
使用者說：跟小每出去玩
```

### 校正提示詞

自動 AI 的固定提示詞之一，和判斷提示詞分開，不含執行器與日期語法（校正不需要知道有哪些執行器，也避免 AI 往指令的方向改寫）：

- 使用者用語音說出對待辦清單的需求，語音辨識可能有同音、近音的錯字。
- 依常識修正錯字；和黑板上待辦內容的人名、名詞發音相近時，改成黑板上的寫法（黑板的每一行是方框、日期、時刻與內容，只看內容）。
- 畫面資訊只是線索，只修正「使用者說」。
- 一個字換一個字，字數和原句相同；不加字、不刪字、不改語序與語氣，不回答問題。
- 沒有錯字就原樣輸出，這是最常見的結果。

輸出結構：`{"text": "<校正後的句子>"}`。

### 採用規則

App 判斷，去掉頭尾空白後依序比較。數字（日期、時間、編號）是語音辨識最少出錯、改錯代價最大的部分，校正不能改（2026-10-08 實測：「第2項」被改成「第1項」、「下週一」被改成「下週二」、「10月6號」被改成「10月12號」）：

| 結果 | 採用 | 除錯 UI 與測試紀錄 |
|---|---|---|
| 字數相同、內容不同 | 校正後的句子 | 原句 → 校正後的句子 |
| 內容相同 | 原句 | 未修改 |
| 改了數字（阿拉伯數字或國字數字的順序不同） | 原句 | 改了數字，不採用 |
| 字數不同 | 原句 | 字數不同，不採用 |
| 呼叫失敗、回應無法解析 | 原句 | 失敗的原因 |
| 不校正 | 原句 | 不校正的原因（手動 AI、這個 AI 沒有校正） |

校正失敗不進入錯誤確認，佇列照常繼續。

### 之後用哪一句

判斷的請求、回話（例如「聽不懂『…』」）都用採用的句子。對話流裡使用者的這句話也顯示採用的句子（見 [ui](ui.md) 的「對話流」）。原文留在除錯 UI 與測試紀錄。

### 紀錄

- 測試紀錄每句話多一行「校正」：上表的內容。呼叫了自動 AI 時，前面另記一行「回應（耗時）：AI 回傳的句子」，和判斷的回應相同，用來比較校正與判斷的速度。判斷的請求（原句）先記，校正的結果在它之後；作廢時多一行「判斷：校正改了句子，作廢原句的判斷，重新判斷」，接著是新句子的判斷請求。
- 複製的測試紀錄開頭，在判斷提示詞、刪除確認提示詞之後列出「校正提示詞」（有校正功能時）。
- 自動 AI 的 console 詳細紀錄和判斷相同（見 [judgment](judgment.md) 的「紀錄」）。

### 自動 AI

- 校正和判斷是不同的職責：提示詞、輸出結構與介面各自獨立（`CorrectionPrompt`、`CorrectionAI`）；呼叫 API、API key 與模型設定共用同一個自動 AI 的實作。
- 只有 Gemini 實作校正。Foundation Models 不校正：它的校正改錯的比改對的多（2026-10-09 實測：「後天」→「明天」、「買牛奶」→「買奶水」，字數與數字都沒變，App 擋不住）。Gemini 的輸出上限 256 token（隱藏的思考也算在內），其他行為（temperature、逾時、錯誤原因）和判斷相同。

## Testing Decisions

- 單元測試（macOS）：
  - 採用規則：字數相同且內容不同才採用；內容相同為未修改；字數不同不採用；先去掉頭尾空白
  - 校正請求：是畫面資訊，「使用者說」是原文（畫面資訊本身的測試見 [screen-info](screen-info.md)）
  - 流程（假的自動 AI）：校正後的句子送進判斷；字數不同、校正丟出錯誤時用原句且不進入錯誤確認；手動 AI 與關鍵字不呼叫校正；重試不再呼叫校正
- 手動驗證（Gemini，除錯 UI 與測試紀錄）：
  - [ ] 「10月6號麵是」→「10月6號面試」
  - [ ] 黑板有「跟小美吃飯」時，「跟小每出去玩」→「跟小美出去玩」
  - [ ] 「看牙醫」「新增」「明天看牙醫」不被改動
  - [ ] 有釐清問題時，簡短回答能被正確修正，或維持原句

## Out of Scope

- 字數會改變的錯字（多字、漏字、黏字）
- 語法、語序、語氣的修正
- 用黑板以外（看不到）的待辦當線索
- Gemini 以外的自動 AI 的校正
- 拆任務（屬於判斷階段）
